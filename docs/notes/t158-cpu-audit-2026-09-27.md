# T158 の表: CPU の速さに効く所を端末の上限と比べる（2026-09-26〜27、Fable の perf-auditor）

## 読み方

- **開発機 = a1-free**（OCI の Ampere A1、Neoverse-N1 × 2、`asimddp` あり）。V8 = Node 24.20 の WebAssembly。カーネルは `make kernels` の `simdkernel_plain.wasm`・`simdkernel_relaxed_plain.wasm`（ページと同じもの）。
- **上限の定義**（T158 の項のとおり）: 計算は「同じ命令だけのループ」（V8 の上で `.tmp/t158/bench.ts`、ネイティブで `.tmp/t158/ceiling2.c` の asm）、帯域は「読み出しだけのループ」（256〜512MB、DRAM）。% = 今の値 ÷ 上限。
- **周波数**: 依存する add の鎖では 2.69 GHz と出たが、SIMD の上限は 2 本のパイプ × 3.0 GHz で説明がつく（SDOT 2 命令/サイクル × 16 積和 × 3.0 GHz = 96 G MAC/s に対して実測 92.5〜93.3。FMLA は 24 に対して 20.3〜23.3）。式には測ったループの値を使い、周波数からの計算は添えるだけ。
- **計測の条件（重要）**: 別の担当が同じ機械で build・pytest・Playwright の Chromium を回していた。**1 本の計測（節 1・2）は 1 分平均の load 1.3〜1.5 のとき**（もう 1 コアは空いていた。best と median の差は数 %）。**2 本と長い文脈の計測（節 3）は load 2.2〜3.5 で無効**（1 本の 1 トークンが記録の 15.8 ms に対して 21.5 ms、36% 遅い。2 本が 1 本と同じ = 相手が 2 コア目を使っていた）。**取り直しは持ち主の判断でやめた（2026-09-27）**: 各 T が実装の前後で自分で測る。節 3 の数字は load を添えて「取り直し無し」。
- 訪問者の端末（節 4）は T134 の報告（持ち主の Android）から。その端末の上限は未計測（T163）。

- **この端末の帯域の上限と SDOT の上限は未計測**（T163 で `/benchmark/` に足す）。分かること: 1 本の 1 トークンが 18.9 GB/s で、a1-free の `matmul_q8r` のキャッシュ内の計算の速さ（18〜20 GB/s 相当）と同じ桁。4 本で 28 GB/s まで伸びるので、**この端末の 1 本は帯域でなく計算で律速されている見込み**（Firefox の 1 本が Chrome の半分で 4 本はほぼ同じ、というのもそれと合う: 1 本はコード生成の差、4 本は帯域の壁）。そうなら 1 トークンの帳簿を減らす形（節 6 の候補）が 1〜2 本の端末で効く。決めるのは T163 の読み出しの行。
- プロンプトは 4 本で 30.8〜43.9 G MAC/s。a1-free の比（T108 の形 15 対 タイル 51〜69）が同じなら 1 本でも 50 G MAC/s 級に届く見込み（未計測。その端末の SDOT の発行率が要る）。
